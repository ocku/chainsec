# Dependency resolution and acquisition

## Supported ecosystems

| Ecosystem | Declarations | Lockfiles | Artifacts |
| --- | --- | --- | --- |
| Python | PEP 621 and Poetry dependencies | `poetry.lock`, `Pipfile.lock`, `uv.lock`, `pdm.lock` | wheels, ZIP, `.tar`, `.tar.gz`, `.tar.bz2`, `.tar.xz` |
| npm | dependencies, optional dependencies, peer dependencies | npm lock/shrinkwrap 1–3, Yarn Classic, pnpm 5.3/5.4/6/9 | integrity-checked npm tarballs |
| Deno | JSON/JSONC imports and scoped imports | `deno.lock` versions 1–5 | bounded HTTP(S) graphs, locked npm tarballs, and manifest-verified JSR packages |
| GitHub | npm and Python Git declarations pinned to a full commit | declaration or supported package lock | bounded `codeload.github.com` source archives (origin-pinned; no independent archive/tree digest) |

Deno URL graphs are syntax-aware rather than full Deno runtime resolution: static HTTP(S) and URL-relative literals in imports, exports, and dynamic `import()` calls are followed. A static literal that the URL graph fetcher cannot materialize—including bare, `npm:`, `jsr:`, `node:`, `data:`, other non-HTTP schemes, custom-loader, or invalid URL-relative specifiers—fails the fetch with a `Deno graph resolution` policy error; ChainSec never reports that graph as complete. Computed/template expressions and escaped literals are outside static-literal discovery and are not resolved. `npm:` and `jsr:` graph imports will remain fail-closed until they can be materialized from integrity-bound Deno lockfile entries. A root-only HTTP(S) graph can be acquired with the declared root integrity and no lockfile. A multi-module HTTP(S) graph requires `deno.lock` `remote` integrity entries for every fetched module, including the root; the root remains independently checked against its declared integrity.

## Remote version diffs

`chainsec remote diff <source:package>` requires exactly one release selector. `--last N` requires `N >= 2`, resolves the package selector normally, then selects that release and up to `N - 1` older integrity-pinnable releases in ecosystem-native version order. `--compare FROM TO` selects exactly those two published endpoints. `--range FROM TO` selects every pullable published release in the inclusive interval. Explicit endpoints must be distinct, with `FROM` older than `TO`, and must themselves be pullable; unsupported intermediate range releases are omitted. Selection fails before downloading root artifacts when the number of versions exceeds `--max-packages`; the same limit then bounds aggregate unique roots and dependency acquisitions across the batch. The convenience form `chainsec remote scan <source:package> --diff N` is equivalent to `remote diff <source:package> --last N`.

npm releases require a supported SRI integrity value (SHA-256 or SHA-512); when multiple supported values are present, ChainSec verifies the strongest algorithm listed. PyPI release selection requires a non-yanked source distribution with a published SHA-256 digest; wheel-only releases are not selected because their contents can vary by Python, ABI, operating system, and architecture. An exact wheel referenced by a supported lockfile remains fetchable when its SHA-256 identifies that artifact. JSR releases must be non-yanked and have fetchable version metadata. All selected roots are downloaded first, their dependency closures are acquired as one deduplicated batch, and each unique package source is scanned once. Separate reports retain each version's own dependency closure and normal traversal and policy semantics. Adjacent reports are compared as older → newer. Detection changes are grouped by risk, finding group, and rule ID; capability changes compare evidence counts by capability name. Human output applies `--fail-on` unless `--verbose` is set; JSON includes every detection. Operational issues are included with their version, mark affected comparisons as incomplete, and determine exit status across all selected versions. Finding-based exit status fails only when at least one unsuppressed occurrence at or above `--fail-on` is present at the newest endpoint without the same normalized package/rule version/file/location/matched-code identity at the oldest endpoint. This identity check detects replacements even when the grouped display count is unchanged; dependency and root package version/integrity changes alone do not make an otherwise unchanged occurrence new. Human and JSON diff reports are supported; SARIF represents a single scan and is not. GitHub full-commit selectors are excluded because GitHub archive selectors do not provide an ordered registry release history. After selection, an artifact download, integrity verification, extraction, policy, or resource-limit failure aborts the diff instead of silently replacing the failed release.

## Limitations and unlocked resolution

Unsupported forms fail or remain unresolved rather than silently selecting `latest`. `--allow-unlocked` is the explicit exception for supported PyPI and npm registry requirements, where the highest pullable release matching the declared version range is selected. For PyPI, pullable unlocked releases must publish a non-yanked source distribution with SHA-256 integrity; ChainSec does not choose an arbitrary wheel from a wheel-only release.

Yarn Berry `npm:` lock entries pin the exact release, but their cache checksums are not npm tarball integrity values. ChainSec obtains the pinned release's tarball URL and integrity from the configured npm registry before download, so scans need `--online` and the registry host must be allowed. Other Berry protocols remain unresolved and fail closed unless separately supported.

Git acquisition is deliberately limited to public GitHub repositories pinned to full 40-hex commits; branches, tags, short revisions, other hosts, submodules, and Git LFS acquisition are unsupported. A GitHub commit selector constrains the canonical codeload request but does not provide an independently verifiable archive or tree digest: ChainSec trusts GitHub, DNS, TLS, and codeload to return the requested commit. Choose an integrity-pinned registry artifact when independent content verification is required.

Python requirements files, workspace graph semantics, environment-marker evaluation, and native/binary semantic analysis are not yet implemented. File-level checks may still flag binary, compressed, and high-entropy files.
